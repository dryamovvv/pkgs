# Технический аудит и обзор репозитория пакетов Arch Linux aarch64

Данный документ представляет собой подробный технический обзор архитектуры монорепозитория `github:dryamovvv/pkgs`, анализ его CI/CD-процессов, аудит качества кода утилит и пакетов, а также перечень найденных уязвимостей, багов и областей для оптимизации.

---

## 1. Архитектура и оптимизация под Raspberry Pi 5

Репозиторий представляет собой высокооптимизированный монорепозиторий пакетов для архитектуры **Arch Linux ARM (aarch64)**. Вся инфраструктура ориентирована на максимальную производительность на процессорах **Broadcom BCM2712 (Cortex-A76)**, используемых в Raspberry Pi 5.

### Аппаратная оптимизация (CFLAGS/CXXFLAGS/LDFLAGS)

Оптимизация компиляции задается в шаблонах `PKGBUILD` и применяется при сборках в контейнерах:

- **`mcpu=cortex-a76+crypto`**: Включает специфичный для Cortex-A76 набор инструкций (ARMv8.2-A), а также криптографические расширения (AES, SHA, PMULL), поддержку CRC, LSE (Large System Extensions), RDMA, FP16, Dot Product и RCPC. Это обеспечивает значительный прирост производительности по сравнению с обобщенным профилем `generic` ARMv8-A.
- **`-O2 -pipe`**: Оптимальный баланс производительности компилятора и результирующего кода с передачей промежуточных данных через конвейеры (без лишних дисковых операций).
- **`-Wl,-z,max-page-size=0x4000`**: Выравнивание сегментов ELF на **16 KB** (размер страницы памяти Raspberry Pi 5). Это критично для ядра `linux-rpi-16k`, так как ELF-файлы, скомпилированные с дефолтным выравниванием 4 KB, не смогут быть загружены на ядре со страницами 16 KB (приведет к ошибке сегментации при запуске).

### Специфичные оптимизации языков программирования

- **Rust**: `RUSTFLAGS="-C target-cpu=cortex-a76 -C opt-level=2"` транслирует оптимизации LLVM непосредственно под микроархитектуру Cortex-A76.
- **Go**: `GOARM64=v8.2` совместно с флагами компоновщика `-extldflags=-Wl,-z,max-page-size=0x4000` гарантирует корректную работу Go-бинарников на 16-килобайтных страницах.

## 2. Анализ CI/CD процессов и жизненного цикла

Автоматизация репозитория построена на GitHub Actions и делится на несколько ключевых этапов:

```text
                  ┌──────────────────────┐
                  │ Git Push / PR Merge  │
                  └──────────┬───────────┘
                             │
                             ▼
               ┌───────────────────────────┐
               │ detect-changed-packages   │ (Выявление измененных пакетов)
               └─────────────┬─────────────┘
                             │
                             ▼
               ┌───────────────────────────┐
               │    build-packages-matrix  │ (Параллельная сборка в Docker)
               └─────────────┬─────────────┘
                             ├─────────────────────────────────┐
                             │ (Успех)                         │ (Ошибка)
                             ▼                                 ▼
               ┌───────────────────────────┐     ┌───────────────────────────┐
               │      deploy-packages      │     │   create-failure-issue    │ (Создание issue)
               └───────────────────────────┘     └─────────────┬─────────────┘
                                                               │
                                                               ▼
                                                 ┌───────────────────────────┐
                                                 │     auto-fix-runner       │ (Попытка автофикса)
                                                 └───────────────────────────┘
```text

### 1. Шаг детектирования (`detect-changed-packages` в `build.yml`)

- Выполняет `git diff --name-only HEAD~1` для поиска изменений в директории `packages/`.
- Корректно обрабатывает начальный коммит репозитория (когда `HEAD~1` не существует), переключаясь на сборку всех пакетов.
- В случае изменения инфраструктурных скриптов в `ci/` или файлов конфигурации воркфлоу запускает полную пересборку всех пакетов.

### 2. Шаг сборки (`build-packages-matrix` в `build.yml`)

- Выполняется на нативных ARM64-раннерах GitHub (`ubuntu-24.04-arm`), что исключает накладные расходы на эмуляцию QEMU.
- Использует детерминированное вычисление хэша сборки (`ci/compute-build-hash.sh`), который учитывает:
  - Содержимое `PKGBUILD` пакета.
  - Контрольные суммы локальных файлов-источников.
  - Текст скрипта сборщика `ci/build-package.sh` (любые глобальные изменения в сборщике инвалидируют кэш).
- Поддерживает кэширование готовых артефактов (`build-artifact-{pkg}-{hash}`). Если пакет с таким хэшем уже собирался, сборка пропускается, экономя время.
- Сборка пакета происходит в изолированном Docker-контейнере `archlinuxarm:base-devel` с использованием `ccache` для повторной компиляции C/C++ кода.

### 3. Шаг автоматического исправления ошибок (`opencode.yml`)

- В случае падения сборки воркфлоу `build.yml` запускает `ci/report-failure.sh`.
- Скрипт парсит логи, выявляет упавшие пакеты и создает/обновляет специальную GitHub Issue с ярлыком `ci-failure` и счетчиком попыток `fix-attempt-N` (лимит: 3 попытки).
- Создание issue триггерит воркфлоу `opencode.yml`, запускающий агента `auto-fix-runner`.
- Агент анализирует логи падения сборки, вносит исправления в `PKGBUILD`, проверяет синтаксис с помощью `bash -n` и базовых проверок полей, коммитит изменения в ветку `auto-fix` и открывает Pull Request.
- После успешного прохождения тестов на PR воркфлоу `auto-merge-on-ci-success.yml` автоматически сливает пул-реквест, а `auto-fix-finalize.yml` закрывает исходную Issue. Это формирует полностью автономный цикл самовосстановления CI/CD.

### 4. Дополнительные инструменты обслуживания

- **`check-updates.sh`**: Опрашивает API GitHub Releases для отслеживания выхода новых версий upstream-проектов и автоматически открывает задачи `modify-package` для обновления.
- **`auto-add-sha256sums.sh`**: Автоматически скачивает исходники пакетов, вычисляет их `sha256sums` и обновляет `PKGBUILD`, избавляя разработчиков от рутины.

## 3. Критическая уязвимость: Ошибка деплоя цифровых подписей пакетов

В ходе анализа скрипта деплоя `ci/deploy-package.sh` была обнаружена **критическая архитектурная уязвимость/баг**, полностью ломающая установку пакетов на конечных устройствах при использовании стандартных мер безопасности Arch Linux.

### Суть проблемы в `ci/deploy-package.sh`

На этапе сбора построенных пакетов для их отправки в релиз скрипт выполняет обход файлов в директории `packages/` и ищет созданные пакеты:

```bash
for pkg_dir in packages/*; do
  # ...
  for f in "$pkg_dir"/*.pkg.tar.*; do
    [ -f "$f" ] || continue
    basename=$(basename "$f")
    if [[ "$basename" == *.sig ]]; then
      continue
    fi
    # ... копирование пакета во временную директорию ...
  done
done
```text

Из-за явного пропуска файлов подписей (`[[ "$basename" == *.sig ]] && continue`), создаваемые файлы `.sig` **никогда не копируются** в рабочую область деплоя (`$WORKDIR`) и, следовательно, **не загружаются в GitHub Releases**.

### Последствия

1. Файлы подписей пакетов (`*.pkg.tar.zst.sig`) отсутствуют в репозитории на хостинге `dryam.ru`.
2. В то же время база данных репозитория (`custom-repo.db.tar.gz`) успешно подписывается приватным ключом.
3. Согласно рекомендуемой в `AGENTS.md` конфигурации pacman:
   ```ini
   [custom-repo]
   SigLevel = Required TrustedOnly
   Server = http://pkgs.dryam.ru/aarch64
   ```
   Уровень безопасности `Required` обязывает pacman проверять подпись для _каждого_ устанавливаемого пакета. Поскольку файлов `.sig` в репозитории нет, **любая попытка установки или обновления пакета завершится критической ошибкой pacman** из-за отсутствия подписи пакета. Пользователи будут вынуждены понижать уровень безопасности до `SigLevel = Optional` или `TrustAll`, что ставит под угрозу безопасность их систем.

## 4. Проблемы качества кода, надежности и производительности

### 1. Хрупкий парсинг регулярных выражений AWK в `compute-build-hash.sh`

Для вычисления хэша сборщика скрипт `ci/compute-build-hash.sh` пытается извлечь массивы `source` и `sha256sums` из `PKGBUILD` с помощью AWK-парсинга строк:

```bash
source_block=$(awk '/^source=\(/,/\)/' "$pkg_dir/PKGBUILD")
sha256_block=$(awk '/^sha256sums=\(/,/\)/' "$pkg_dir/PKGBUILD")
```text

**Почему это хрупко:**

- Если массив записан в одну строку (например, `source=("https://example.com/file.tar.gz")`), парсер AWK не совпадет по интервалу регулярных выражений и вернет пустую строку или сломается.
- Если внутри блока присутствуют однострочные комментарии со скобками, это нарушит границы поиска.
- **Решение**: Использовать безопасное изолированное профилирование (sourcing) файла `PKGBUILD` в bash-окружении (как это сделано в `auto-add-sha256sums.sh`), где переменные становятся доступны нативно.

### 2. Ручное клонирование Git-репозиториев в `prepare()`

В пакете `packages/mozillavpn/PKGBUILD` в секции `prepare()` выполняется ручной вызов `git clone`:

```bash
git clone --depth=1 --branch "v$pkgver" "https://github.com/mozilla-mobile/mozilla-vpn-client.git" "$pkgname-$pkgver"
```text

**Почему это плохо:**

- **Обход кэширования makepkg**: Стандартный механизм Arch Linux `makepkg` умеет кэшировать git-источники, если они указаны в массиве `source=()`. Ручной клон скачивает весь репозиторий заново при каждой сборке, увеличивая нагрузку на сеть и замедляя CI.
- **Сбой вычисления хэша**: Скрипт `compute-build-hash.sh` не может отслеживать изменения в таком git-источнике, так как URL не зарегистрирован в массиве `source`. Это может приводить к ложным кэш-хитам (cache-hits) и деплою устаревших бинарников.
- **Решение**: Использовать нативный формат источников `source=("git+https://github.com/mozilla-mobile/mozilla-vpn-client.git#tag=v$pkgver")`.

### 3. Модификация глобального окружения в контейнере сборщика

В том же пакете `mozillavpn` внутри `prepare()` запускается:

```bash
pip install --break-system-packages glean_parser
```text

Хотя сборка происходит внутри изолированного Docker-контейнера, установка python-пакетов глобально через `--break-system-packages` является плохой практикой. При усложнении репозитория это может вызвать конфликты версий зависимостей между разными пакетами на одном этапе сборки.

- **Решение**: Устанавливать утилиту в виртуальное окружение (venv) внутри `$srcdir` или оформить `glean_parser` как отдельный сборочный пакет (makedepends) репозитория.

### 4. Медленная сборка из-за отсутствия многопоточности (`MAKEFLAGS`)

В скрипте `ci/build-package.sh` настраиваются оптимизации компилятора в `/etc/makepkg.conf`, однако полностью отсутствует директива `MAKEFLAGS`:

```bash
# В ci/build-package.sh настраиваются CFLAGS/CXXFLAGS, но нет MAKEFLAGS
```text

По умолчанию `makepkg` запускает утилиту `make` (и другие сборочные инструменты) в один поток. На мощных 8-ядерных ARM64 раннерах GitHub Actions (`ubuntu-24.04-arm`) это приводит к колоссальной потере времени компиляции (пакеты собираются в 8 раз медленнее, чем могли бы).

- **Решение**: Добавить `MAKEFLAGS="-j$(nproc)"` в конфиг `makepkg.conf` внутри сборочного контейнера.

### 5. Ограничения логики автоматического поиска обновлений

Утилита `ci/check-updates.sh` проверяет обновления исключительно через обращения к API GitHub Releases (`releases/latest`). Многие системные библиотеки и пакеты Arch Linux не используют функционал релизов GitHub, а публикуют обновления только в виде git-тегов (например, тот же `kmscon` или `arch-opsd`). Подобные пакеты никогда не будут автоматически обновлены этой утилитой.

- **Решение**: Добавить поддержку проверки обновлений по git-тегам или использовать системный инструмент проверки `archco` / `nvchecker`.

## 5. Сводные рекомендации и план действий

1. **Исправление деплоя подписей (Критично)**:
   В файле `ci/deploy-package.sh` заменить логику сбора пакетов, чтобы файлы `.sig` копировались вместе с самими пакетами во временную директорию перед отправкой в релиз.
2. **Включение многопоточности сборки (Высокий приоритет)**:
   В `ci/build-package.sh` добавить:

   ```bash
   echo 'MAKEFLAGS="-j$(nproc)"' >> /etc/makepkg.conf
   ```

   Это сократит время сборки больших пакетов (таких как `helix`, `atuin`, `mozillavpn`) на CI раннерах на 70-80%.

3. **Рефакторинг `compute-build-hash.sh` (Средний приоритет)**:
   Перейти от AWK-парсинга к нативному импорту переменных `source` и `sha256sums` путем безопасного изолированного выполнения `PKGBUILD` в подоболочке bash, гарантируя 100% стабильность кэширования.

4. **Оптимизация пакета `mozillavpn` (Средний приоритет)**:
   Переписать `PKGBUILD` для использования нативного механизма git-источников `source=()`, избавившись от ручного `git clone` и глобального запуска `pip install`.
